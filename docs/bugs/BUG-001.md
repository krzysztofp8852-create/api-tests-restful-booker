# BUG-001: Invalid booking payloads return 500 instead of 4xx

| Field | Value |
|---|---|
| ID | BUG-001 |
| Title | Missing `firstname` / `lastname` or an empty body causes Internal Server Error |
| Severity | Major |
| Priority | P2 |
| Status | Open |
| Environment | Restful Booker · `https://restful-booker.herokuapp.com` |
| Endpoint | `POST /booking` |
| Found in | TC-010, TC-018, TC-030 (evidence: TC-029, TC-034) |
| Date | 2026-08-13 (re-verified 2026-09-09) |
| Author | Krzysztof Pabich |

## Summary

`POST /booking` responds with **500 Internal Server Error** whenever a required string field is missing, or when the request has no body at all. The server should reject an invalid payload with a client error instead of failing internally.

## Preconditions

- API is up (`GET /ping` → 201)

## Steps to reproduce

1. `POST /booking` with JSON **without** `firstname`:

```json
{
  "lastname": "Tester",
  "totalprice": 120,
  "depositpaid": true,
  "bookingdates": {
    "checkin": "2026-09-16",
    "checkout": "2026-09-20"
  }
}
```

2. Repeat with `firstname` present and `lastname` omitted (TC-018).
3. Repeat with an empty request body and `Content-Type: application/json` (TC-030).

## Expected result

HTTP **400** (or another 4xx). Body explains which field is missing. No `bookingid`. No 5xx.

## Actual result

| Case | Status | Body |
|---|---|---|
| TC-010 — no `firstname` | **500** | `Internal Server Error` (`text/plain`) |
| TC-018 — no `lastname` | **500** | `Internal Server Error` (`text/plain`) |
| TC-030 — empty body | **500** | `Internal Server Error` (`text/plain`) |

## Evidence that this is a validation gap, not intended behaviour

Two neighbouring cases prove the API is able to answer with 400 on the same kind of input, which makes the 500 above an unhandled exception rather than a design choice:

| Case | Request | Status |
|---|---|---|
| TC-029 | `POST /booking` with syntactically broken JSON | **400** `Bad Request` |
| TC-034 | `PUT /booking/:id` **without** `lastname` | **400** `Bad Request` |

So the same missing-field payload is validated on `PUT` and crashes on `POST`. The validation layer exists; it is simply not wired into the create path.

## Evidence

- [x] Reproduced at least three times: `firstname` missing, `lastname` missing, empty body
- [x] Date/time of reproduction: 2026-09-09
- Covered by Newman: `TC-010 POST Create booking — missing firstname`, `TC-018 POST Create booking — missing lastname`, `TC-030 POST Create booking — empty request body`

## Workaround

Validate required fields on the client before calling the API.

## Notes

Identical 500 for all three inputs suggests one unhandled exception during persistence. Fixing the create path to reuse the `PUT` validator would close TC-010, TC-018 and TC-030 at once.
