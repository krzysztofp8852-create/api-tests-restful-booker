# BUG-004: Unparsable date is stored as the literal string `0NaN-aN-aN`

| Field | Value |
|---|---|
| ID | BUG-004 |
| Title | `POST /booking` accepts a non-date and persists `0NaN-aN-aN` |
| Severity | Major |
| Priority | P2 |
| Status | Open |
| Environment | Restful Booker · `https://restful-booker.herokuapp.com` |
| Endpoint | `POST /booking` |
| Found in | TC-031 |
| Date | 2026-09-09 |
| Author | Krzysztof Pabich |

## Summary

`POST /booking` accepts any string in `bookingdates.checkin` / `bookingdates.checkout`. A value that cannot be parsed as a date is not rejected — it is run through a date formatter whose `NaN` output is stored verbatim, producing the literal string `0NaN-aN-aN` in the booking.

This is worse than a plain validation gap: the API creates a record that no longer satisfies its own response contract, so every consumer that parses `checkin` as a date breaks on that booking. The corrupt booking is also returned by `GET /booking/:id` and counted by the date filters.

## Preconditions

- API is up (`GET /ping` → 201)

## Steps to reproduce

1. `POST /booking` with JSON:

```json
{
  "firstname": "Krzysztof",
  "lastname": "Tester",
  "totalprice": 120,
  "depositpaid": true,
  "bookingdates": {
    "checkin": "not-a-date",
    "checkout": "2026-09-20"
  }
}
```

2. Note the `bookingid` in the response and read it back with `GET /booking/{bookingid}`.

## Expected result

HTTP **400**. Body states that `checkin` must be an ISO date (`YYYY-MM-DD`). No `bookingid`.

## Actual result

- HTTP status: **200**
- Body (trimmed):

```json
{
  "bookingid": 4624,
  "booking": {
    "firstname": "Krzysztof",
    "lastname": "Tester",
    "totalprice": 120,
    "depositpaid": true,
    "bookingdates": {
      "checkin": "0NaN-aN-aN",
      "checkout": "2026-09-20"
    }
  }
}
```

The same `0NaN-aN-aN` value is returned by a later `GET /booking/{bookingid}`, so it is persisted, not just echoed.

## Evidence

- [x] Reproduced at least twice: yes
- [x] Date/time of reproduction: 2026-09-09
- Covered by Newman: `TC-031 POST Create booking — unparsable date` — asserts both the literal `0NaN-aN-aN` and that the stored value violates the `YYYY-MM-DD` contract

## Workaround

Validate the date format on the client. When reading bookings, treat a `bookingdates` value that does not match `^\d{4}-\d{2}-\d{2}$` as corrupt rather than passing it to a date parser.

## Notes

The `0NaN-aN-aN` shape (year `0NaN`, month `aN`, day `aN`) points at a hand-rolled formatter concatenating the parts of an `Invalid Date` instead of checking it. Rejecting unparsable input at the create path would fix this and also help [BUG-002](BUG-002.md), which lacks a range check on the same field pair.
