# BUG-006: XML response is served with `Content-Type: text/html`

| Field | Value |
|---|---|
| ID | BUG-006 |
| Title | `Accept: application/xml` returns an XML body labelled as `text/html` |
| Severity | Minor |
| Priority | P3 |
| Status | Open |
| Environment | Restful Booker · `https://restful-booker.herokuapp.com` |
| Endpoint | `GET /booking/:id` |
| Found in | TC-027 |
| Date | 2026-09-09 |
| Author | Krzysztof Pabich |

## Summary

Requesting a booking with `Accept: application/xml` correctly returns an XML document, but the response declares `Content-Type: text/html; charset=utf-8`. A client that dispatches on the response media type — as any generated API client does — will hand an XML payload to an HTML parser.

## Preconditions

- API is up (`GET /ping` → 201)
- A booking exists (`POST /booking` → `bookingid`)

## Steps to reproduce

1. `GET /booking/{bookingid}` with header `Accept: application/xml`
2. Inspect the response headers and the body.

## Expected result

- HTTP **200**
- `Content-Type: application/xml` (or `text/xml`), matching the payload
- XML body

## Actual result

- HTTP status: **200**
- `Content-Type: text/html; charset=utf-8`
- Body is valid XML:

```xml
<?xml version='1.0'?>
<booking>
    <firstname>Krzysztof</firstname>
    <lastname>Tester</lastname>
    <totalprice>120</totalprice>
    <depositpaid>true</depositpaid>
    <bookingdates>
        <checkin>2026-09-16</checkin>
        <checkout>2026-09-20</checkout>
    </bookingdates>
    <additionalneeds>Breakfast</additionalneeds>
</booking>
```

For comparison, the JSON variant of the same resource is labelled correctly: `Accept: application/json` → `Content-Type: application/json; charset=utf-8`.

## Evidence

- [x] Reproduced at least twice: yes
- [x] Date/time of reproduction: 2026-09-09
- Covered by Newman: `TC-027 GET Booking by id — Accept: application/xml` — asserts the XML payload parses and that the header is currently `text/html`, so the test flips to failing once the media type is corrected

## Workaround

Ignore the response `Content-Type` for the XML variant and select the parser from the `Accept` header the client sent.

## Notes

Only the media type is wrong; the serialisation itself is correct. Related to [BUG-007](BUG-007.md), which covers the same content-negotiation code path for media types the API does not support at all.
