# BUG-007: Unsupported `Accept` type returns 418 instead of 406

| Field | Value |
|---|---|
| ID | BUG-007 |
| Title | Content negotiation answers `418 I'm a teapot` for unsupported media types |
| Severity | Minor |
| Priority | P3 |
| Status | Open |
| Environment | Restful Booker · `https://restful-booker.herokuapp.com` |
| Endpoint | `GET /booking/:id` |
| Found in | TC-042 |
| Date | 2026-09-09 |
| Author | Krzysztof Pabich |

## Summary

When the client asks for a media type the API cannot produce, the response is **418 I'm a teapot** instead of **406 Not Acceptable**. 418 is a joke status with no defined semantics, so a client cannot tell an unsupported format from a server malfunction, and generic HTTP error handling (retry, fallback, logging) treats it as an unknown failure.

## Preconditions

- API is up (`GET /ping` → 201)
- A booking exists (`POST /booking` → `bookingid`)

## Steps to reproduce

1. `GET /booking/{bookingid}` with header `Accept: application/pdf`
2. Repeat with `Accept: text/xml`, `Accept: text/plain`, `Accept: text/html`, `Accept: application/xhtml+xml`

## Expected result

HTTP **406 Not Acceptable** (RFC 9110 §15.5.7), optionally listing the supported media types.

## Actual result

Every unsupported media type gives the same response:

- HTTP status: **418 I'm a teapot**
- `Content-Type: text/plain; charset=utf-8`
- Body: `I'm a Teapot`

| `Accept` | Status |
|---|---|
| `application/json` | 200 (JSON) |
| `*/*` (default) | 200 (JSON) |
| `application/xml` | 200 (XML, mislabelled — see [BUG-006](BUG-006.md)) |
| `text/xml` | **418** |
| `text/plain` | **418** |
| `text/html` | **418** |
| `application/xhtml+xml` | **418** |
| `application/pdf` | **418** |

Notable: `text/xml` is a standard alias for `application/xml`, and the API supports XML — yet asking for it with the alias fails.

## Evidence

- [x] Reproduced across five different media types
- [x] Date/time of reproduction: 2026-09-09
- Covered by Newman: `TC-042 GET Booking by id — unsupported Accept type`, which also asserts that the error body leaks no booking data

## Workaround

Always send `Accept: application/json` (or omit the header) unless the XML variant is needed, in which case send exactly `application/xml`.

## Notes

Two fixes are worth separating: answer 406 for genuinely unsupported types, and treat `text/xml` as an alias of `application/xml` so the supported format is reachable under both names.
